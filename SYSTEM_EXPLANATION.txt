PART A: FOR A COMPUTER SCIENCE PROFESSOR

OVERVIEW
--------
This system is a production-grade Retrieval-Augmented Generation (RAG)
pipeline tailored to legal document question-answering. It goes beyond the
standard dense-retrieval + generation baseline in four substantive ways:
(1) hybrid lexical-semantic retrieval with Reciprocal Rank Fusion,
(2) Summary-Augmented Chunking to address the semantic gap between short
    document fragments and short user queries,
(3) a learned query router that gates between local LLM inference, a GPU
    cluster (Mixtral 8x7B), and a rule-based temporal reasoning sub-system,
(4) a session memory layer with factual compression and constraint extraction.

The evaluation harness compares five RAG configurations across six
established, English-language benchmark datasets from the legal NLP
literature — one dataset per research question (RQ2, session memory, is
covered by two: a factual-memory and a cognitive-memory benchmark) plus one
generalisation check — covering thirteen distinct metrics including
ROUGE-L, exact match, token F1, macro-F1, AUPR, precision-at-recall,
LLM-as-judge scores, and retrieval recall. Results are persisted to
PostgreSQL and visualised in an interactive dashboard.

--------------------------------------------------------------------------------
1. INGESTION PIPELINE
--------------------------------------------------------------------------------

PDF text extraction uses PyMuPDF (libmupdf bindings) rather than pypdf.
The distinction matters for legal documents: ICJ/ICC decisions are produced
with proprietary PDF workflows that embed non-standard font encoding tables.
pypdf's pure-Python decoder misinterprets the glyph mapping, producing
character-spacing artefacts ("T h e   l e g a l   f r a m e w o r k")
that corrupt downstream embedding quality. PyMuPDF delegates to the
native mupdf rendering engine which resolves encoding via the font's
CMap tables directly.

Pages are extracted as a list of (page_number, text) tuples. Page numbers
are 1-indexed and preserved through the entire pipeline.

SUMMARY-AUGMENTED CHUNKING (SAC)
For legal documents, a 150-character document-level summary is generated
once via llama3.2:3b (a small, fast model). Every text chunk produced from
that document is then prefixed with "[DOC: <summary>]". The rationale is
the "lost-in-middle" problem specific to legal text: a dense embedding of
"Article 25(2)(b) of the Rome Statute provides that..." will not match a
user query like "what is the legal basis here?" because the query and chunk
have almost disjoint vocabulary. The summary prefix provides a semantic
anchor that is thematically closer to typical query language.

Chunking uses LangChain's RecursiveCharacterTextSplitter with
chunk_size=512, chunk_overlap=50, and hierarchy ["\n\n", "\n", ".", " "].
Critically, the splitter is invoked via create_documents(texts, metadatas)
rather than split_text() on concatenated text. This is the key to accurate
page attribution: each page's text is passed as a separate element in the
texts list with its page number in the corresponding metadata entry.
The splitter propagates source metadata to each output Document object, so
every chunk inherits the correct page number from the page it originated on.
This avoids the naive bug of inferring page numbers from character offsets,
which fails when page lengths vary.

A minimum fragment filter (_MIN_CHUNK_CHARS = 80 characters) discards
header/footer lines. Legal PDFs often have recurring page headers like
"ICC-01/14-01/18-2906   14-04-2026   11/22" which are only 30-40 characters
and carry no semantic content but consume a Qdrant point slot and pollute
nearest-neighbour results.

For application documentation (Markdown API docs, READMEs), the SAC
summary step is skipped — plain chunking is applied with the same splitter
and page-preservation logic.

VECTOR STORE
Each chunk is embedded with nomic-embed-text (768 dimensions) to produce a
dense vector. A sparse BM25-approximation vector is also computed:
tokens are lower-cased, hash-bucketed into a 30,000-dimensional space,
and weighted by TF * log(1 + TF). Both vectors are stored in Qdrant, which
natively supports named vector fields. Collections (legal_docs, app_docs)
are created with:
  vectors_config: {"dense": VectorParams(size=768, distance=COSINE)}
  sparse_vectors_config: {"sparse": SparseVectorParams(...)}

Idempotent re-ingestion: before inserting a document, all existing Qdrant
points matching the filename are deleted using a Filter(FieldCondition(...))
payload scan. This prevents stale chunks from a previous version of a
document accumulating in the index.

Document metadata (filename, source_type, chunk_count, per-chunk Qdrant
point UUIDs) is written to PostgreSQL via SQLAlchemy ORM.

--------------------------------------------------------------------------------
2. RETRIEVAL — HYBRID RRF
--------------------------------------------------------------------------------

At query time, both the dense and sparse representations of the query are
computed. Two Prefetch objects are submitted to Qdrant:
  Prefetch(query=dense_vec, using="dense", limit=top_k*2)
  Prefetch(query=SparseVector(indices, values), using="sparse", limit=top_k*2)

These are fused with FusionQuery(fusion=Fusion.RRF), which applies
Reciprocal Rank Fusion: score(d) = sum_i 1 / (k + rank_i(d)), k=60.
This is Qdrant's native implementation; no post-processing aggregation
in application code is required.

The hybrid query runs against both collections (legal_docs, app_docs)
independently. Results are merged, sorted by score, and the top_k=8
candidates retained.

LOST-IN-THE-MIDDLE REORDERING
LLM attention scores degrade for tokens in the middle of long contexts
(the lost-in-the-middle phenomenon, Liu et al. 2023). The retriever
applies a reordering heuristic: rank-1 result is placed at position 0,
rank-2 result at the last position, and ranks 3..N fill the middle
positions in order. This ensures the most relevant chunks occupy the
high-attention positions (prompt start and end) regardless of what the
LLM's context window length is.

Each result is tagged with source_type ("legal" or "app_docs") for
downstream prompt construction.

Fallback: if the hybrid query throws (e.g., sparse index not populated),
the system falls back to dense-only query silently. This handles the case
where sparse vectors weren't indexed for a particular collection.

--------------------------------------------------------------------------------
3. QUERY ROUTING — ADAPTIVE MoE-STYLE DISPATCHER
--------------------------------------------------------------------------------

The router (self_router.py) operates in two stages, both O(1) or O(n)
in query length — no LLM call is made for routing decisions.

STAGE 1 — TEMPORAL KEYWORD SCAN (zero cost)
A hardcoded list of 18 temporal keywords is matched against the
lowercased query. Keywords include legal-domain terms like
"statute of limitations", "time-bar", "accrual", "notice period",
"within N days of", and generic temporal terms.
Positive match → route = "temporal", bypassing all LLM stages.

STAGE 2 — COMPLEXITY SCORING (O(n) keyword scan)
For non-temporal queries, a lightweight complexity function counts
"analysis signals" (words like "analyse", "compare", "implications",
"comprehensive", "critically") and measures query word count.
  word_count > 40 OR signals >= 2 → confidence = 0.50 → route = "cluster"
  otherwise                        → confidence = 0.85 → route = "local"

The confidence threshold is 0.75. This approach avoids the wasteful
pattern of generating a speculative draft and scoring its log-probabilities
(as in the original Self-RAG and speculative decoding papers), because
generating a draft for routing purposes alone is expensive and the draft
is immediately discarded. Complexity signals from the query itself are
sufficient proxies for whether the answer requires multi-hop reasoning
(→ cluster) or factual retrieval (→ local).

EXPERT ROLE SELECTION
A keyword-based dispatch table maps query content to one of four roles:
"contract law expert", "case law expert", "temporal reasoning expert",
"software documentation expert", "legal assistant". This role is injected
into the system prompt and steers the LLM's output register.

--------------------------------------------------------------------------------
4. GENERATION — SYSTEM PROMPT ASSEMBLY AND STREAMING
--------------------------------------------------------------------------------

PROMPT ARCHITECTURE (priority-ordered sections)
The system prompt is assembled as a structured document with 7 ordered
sections, highest-priority first:

  [PERMANENT CONSTRAINTS]    — cross-session user-set rules (jurisdiction, etc.)
  [SESSION CONSTRAINTS]      — within-session rules
  [EXPERT ROLE]              — role + four grounding rules
  [CONVERSATION SUMMARY]     — factual compression of old turns
  [RETRIEVED CONTEXT]        — source chunks with document/page labels
  [TEMPORAL FACTS]           — output from temporal circuits (if triggered)
  [RECENT MESSAGES]          — last N raw turns (N=4 by default)

The grounding rules injected with the expert role are enforced by the
system prompt, not by post-processing: "Answer ONLY using information from
[RETRIEVED CONTEXT]. Do NOT use prior knowledge. If not found, say exactly:
'I could not find this information in the provided documents.'"

This mirrors the RLHF-grounded instruction-following behaviour of
instruction-tuned models — stating the constraint explicitly in the
system section is more reliable than relying on the model's default
behaviour for attribution.

STREAMING DELIVERY
Responses are streamed over Server-Sent Events (SSE) using FastAPI's
StreamingResponse. The generator yields typed event tuples:
  ("route", path_name, {expert_role, confidence})   — routing decision
  ("status", message, None)                          — e.g. cluster submit
  ("token", word_with_space, None)                   — streaming tokens
  ("temporal_facts", "", {parallel, series, ...})    — date computations
  ("source", source_dict, None)                      — retrieved chunks
  ("done", "", {temporal_result})                    — completion
  ("error", message, None)                           — error

The frontend receives these on a persistent SSE connection and renders
them progressively, including the routing badge and source citations in
real time.

CLUSTER DISPATCH (MIXTRAL 8x7B)
When Mixtral is selected (either by user toggle or by routing to "cluster"),
dispatch_to_cluster_sync() is called inside asyncio.to_thread(). This is
the correct approach: the function does synchronous I/O (SSH subprocess,
polling a shared filesystem), and blocking in an async generator would
starve the FastAPI event loop. Running it in a thread pool allows the
SSE stream to stay alive and deliver the "Submitting to Mixtral..." status
event while waiting.

The cluster dispatch protocol:
  1. Write JSON payload to a shared NFS path (SSHFS mount or scp).
  2. Submit a Slurm sbatch job that reads the JSON, runs inference, writes
     output JSON to a paired output path.
  3. Poll for output file existence (1-second intervals, 600s timeout).
  4. Read and return the output JSON.
  5. If timeout: fall back to local llama3.1:8b via the fallback_fn argument.

On the cluster, cluster_inference.py loads Mixtral-8x7B-Instruct-v0.1
via HuggingFace transformers with BitsAndBytesConfig 4-bit NF4 quantization
(double_quant=True, compute_dtype=bfloat16). 4-bit NF4 (Normal Float 4)
uses a non-uniform quantization grid fitted to the weight distribution of
pre-trained neural networks, which reduces perplexity degradation vs naive
INT4. BF16 compute avoids FP16 overflow on the A40 GPUs (wmlg-ada partition).
With 4-bit quantization, the 47B-parameter sparse model (13B active per
token) fits within one A40 (48 GB VRAM) thanks to the MoE architecture —
only 2 of 8 experts activate per token, so peak memory is much lower than
a dense 47B model would need at full precision.

--------------------------------------------------------------------------------
5. TEMPORAL REASONING SUB-SYSTEM
--------------------------------------------------------------------------------

EXTRACTION (llama3.2:3b structured output)
When the router sends a query to the temporal path, the combined text of
the query and all retrieved chunks is passed to llama3.2:3b with a
structured-output prompt requesting a JSON object with three fields:
  explicit_dates:  [{date: ISO-8601, context: string}]
  trigger_events:  [{event: string, date: ISO-8601 | null}]
  relative_refs:   [string]   — e.g. "within 30 days"

The raw output is parsed by finding the first/last JSON braces, then
validated with python-dateutil for all date strings. Invalid dates are
silently dropped. A Pydantic model enforces the schema.

LOGIC CIRCUITS (zero LLM calls)
Two deterministic circuits run on the extracted data:

  parallel_circuit: Computes earliest/latest date from explicit_dates.
    Detects conflicts: if any relative_ref contains "within N days" and
    the span between earliest and latest exceeds N, a conflict is logged.

  series_circuit: Finds the earliest trigger event with a known date.
    Adds rule_days (extracted from relative_refs via regex) to compute
    a deadline. Default rule_days = 30 if no relative reference found.

The circuit outputs are injected into the system prompt as [TEMPORAL FACTS]
and also streamed to the frontend as a "temporal_facts" SSE event, where
they render as a dedicated date timeline card.

This design separates the non-deterministic extraction step (LLM call,
O(context_length)) from the deterministic computation step (pure Python,
O(n_dates)), making the temporal pipeline both testable and auditable.

--------------------------------------------------------------------------------
6. SESSION MEMORY
--------------------------------------------------------------------------------

CONSTRAINT EXTRACTION (per turn)
On every user message, llama3.2:3b is run with a constraint extraction
prompt that identifies if the user is stating a rule for the conversation
(jurisdiction, financial threshold, applicable law, excluded clauses, etc.).
Extracted constraints are persisted to the Postgres `constraints` table
with is_permanent=True if the user used language like "always" or "in all
sessions". Permanent constraints are loaded across all sessions for the
same user_id.

FACTUAL COMPRESSION (every 10 turns)
After every 10th turn (turn_count % 10 == 0), all but the last 4 messages
are compressed into a factual summary by llama3.1:8b. The prompt instructs
the model to preserve "legal conclusions reached, constraints set, key facts,
document references" and discard filler. The summary replaces the growing
message list in the session context, bounding context window usage.

LOADING ORDER
Session context is assembled in strict priority order:
  1. Permanent constraints (highest priority — must never be overridden)
  2. Session-scoped constraints
  3. Session summary (compressed history)
  4. Last 4 raw messages (most recent context)
This order is mirrored in the system prompt section ordering.

OBSIDIAN INTEGRATION
An optional obsidian_writer module serialises each Q&A turn as a Markdown
file in a configurable Obsidian vault path, with YAML frontmatter (date,
session, route_path, sources). This provides a human-readable audit trail
alongside the Postgres record.

--------------------------------------------------------------------------------
7. EVALUATION FRAMEWORK
--------------------------------------------------------------------------------

The evaluation harness (backend/evaluation/) consists of three modules:
  download_datasets.py  — fetches the 3 auto-fetchable benchmark datasets
                          (LoCoMo/LoCoMo-Plus, CaseHOLD, CUAD) to data/eval/
  benchmarks.py         — loads datasets, runs per-config generation+scoring
  metrics.py            — 13 pure-Python metric implementations

There is no in-app or API-triggered "download all" feature. ContractNLI and
TimeQA are not fetched by any automated code in this codebase at all — both
were obtained once, manually, from their original sources and their
data/eval/*.json files committed directly; see benchmarks.py's
_load_contractnli/_load_timeqa docstrings for exactly where from and in
what shape. The other three (LoCoMo/LoCoMo-Plus, CaseHOLD, CUAD) do have
download_datasets.py functions, but those are run by hand via its CLI
(`python backend/evaluation/download_datasets.py`), never triggered from
the running application.

The FastAPI server exposes the run/monitor/results lifecycle via
/evaluation/run, /evaluation/stop, /evaluation/status, /evaluation/results,
and /evaluation/results (DELETE) — deliberately not a download endpoint.
The frontend EvalDashboard polls /status every 5 seconds unconditionally
(not gated on local state) so the running indicator always reflects server
truth — avoiding a race condition where a fast-finishing task's state would
be missed by a conditional poller.

--------------------------------------------------------------------------------
7a. FIVE RAG CONFIGURATIONS
--------------------------------------------------------------------------------

Each configuration is a distinct variant of the pipeline. Running a benchmark
against all five isolates the contribution of each architectural decision.

  vanilla_rag
    Retrieval:  Dense-only Qdrant query, top-5 results.
    Prompt:     Flat "Context:\n{chunks}\n\nQuestion: {q}\n\nAnswer:"
    Routing:    None — every query goes to local llama3.1:8b.
    Memory:     None.
    Purpose:    Weakest baseline; sets the floor for all comparisons.

  long_ctx_only
    Retrieval:  Dense-only, top-15 results (3× more context than vanilla).
    Prompt:     "You have access to the following document excerpts:\n{15 chunks}"
    Routing:    None — every query goes to local llama3.1:8b.
    Memory:     None.
    Purpose:    Tests whether naively stuffing more context into the prompt
                helps. Isolates context window size from retrieval quality.

  self_route_base
    Retrieval:  Hybrid RRF (dense + sparse, top-8). Correct retrieval approach.
    Prompt:     "You are a {expert_role}.\nContext:\n{chunks}\n\nQuestion:..."
                Expert role injected but no grounding rules, no memory sections.
    Routing:    Full query router active (temporal/local/cluster).
    Memory:     None.
    Purpose:    Tests routing + hybrid retrieval in isolation, without the
                structured prompt discipline of the full system.

  full_system
    Retrieval:  Hybrid RRF (dense + sparse, top-8) with lost-in-middle reorder.
    Prompt:     Full 7-section structured prompt (see Section 4).
                Grounding rules, constraints, compression summary, all active.
    Routing:    Full router. Temporal circuit fires on date keywords.
    Memory:     Constraint extraction + factual compression active.
    Purpose:    The dissertation's primary system. Should outperform all
                other configs on all metrics if the design decisions are sound.

  mixtral_cluster
    Retrieval:  Identical to full_system.
    Prompt:     Identical to full_system.
    Routing:    Identical to full_system.
    LLM:        Mixtral-8x7B-Instruct-v0.1 (4-bit NF4) on Warwick A40 GPU.
    Purpose:    Tests whether model scale alone improves performance above
                the full_system config using llama3.1:8b.

--------------------------------------------------------------------------------
7b. SIX BENCHMARK DATASETS
--------------------------------------------------------------------------------

All six are English-language, so cross-lingual confounds are removed
entirely (the earlier suite included LexRAG and ChronoQA, both Chinese —
see "Retired datasets" note at the end of this section, which are not just
excluded but removed from the codebase entirely). Sourcing is mixed: direct
GitHub downloads are used for LoCoMo/LoCoMo-Plus, a license-gated direct
download is used for ContractNLI, a direct GitHub download (sampled down at
fetch time) is used for TimeQA, and the HuggingFace datasets library is
used for CaseHOLD and CUAD. No deprecated dataset loading scripts are used
— CaseHOLD is accessed via the coastalcph/lex_glue Parquet distribution
(case_hold config) rather than the original reglab/casehold which uses a
broken loading script. There is no in-app or CLI "download all" feature —
see Section 7's intro for exactly how each dataset's data/eval/*.json file
is obtained.

Datasets map one-to-one onto the research questions, plus one held-out
generalisation check. RQ2 (session memory) is split across two datasets —
LoCoMo for the factual-memory score, LoCoMo-Plus for the cognitive-memory
score — since they test genuinely different capabilities (recalling a fact
vs. spontaneously applying an implicit, unprompted cue):
  RQ1 — CUAD, ContractNLI (full CUAD entry appears later in this section)
  RQ2 — LoCoMo (factual memory), LoCoMo-Plus (cognitive memory)
  RQ3 — TimeQA
  Generalisation — CaseHOLD

── ContractNLI ─────────────────────────────────────────────────────────────
Source:     Stanford NLP Group (stanfordnlp.github.io/contract-nli/).
            License-gated direct download (click-through CC BY 4.0 licence,
            no registration wait).
Size:       607 NDAs, split 423/61/123 (train/dev/test) by document. Each
            document is checked against 17 fixed hypotheses, giving 10,319
            (document, hypothesis) pairs, split 7,191/1,037/2,091. The harness
            evaluates a fixed random sample of 1,000 of these 2,091 test
            pairs (same sampling protocol as CUAD, LoCoMo and TimeQA).
Language:   English
Domain:     Non-disclosure agreement (NDA) natural language inference, with
            gold evidence-span annotations (avg. 77.8 candidate spans/doc).

Format:
  Each (document, hypothesis) pair has:
    document       — full NDA text, pre-segmented into candidate spans
    hypothesis     — one of 17 fixed hypotheses, e.g. "Some obligations of
                     Agreement may survive termination."
    label          — Entailment | Contradiction | NotMentioned
    evidence_spans — indices of the spans that support the label (empty
                     for NotMentioned)

How it is evaluated:
  The model receives the NDA text and hypothesis and must (1) classify the
  3-way label and (2) identify which spans constitute evidence, mirroring
  the original paper's own evaluation protocol (Koreeda & Manning, 2021):

  accuracy                        — 1.0 if the predicted 3-way label
                                     matches gold, else 0.0.
  precision_at_recall (r=0.8)     — Of the spans returned once recall
                                     against the gold evidence set reaches
                                     0.8, what fraction are correct. This
                                     is the paper's own headline evidence-
                                     identification metric (P@R0.8).
  micro_f1                        — Micro-averaged precision/recall/F1
                                     treating evidence identification as
                                     multi-label classification over
                                     candidate spans.
  rouge_l                         — supplementary lexical overlap against
                                     the label string.

Significance:
  ContractNLI replaces LegalBench-RAG's three contract_nli_* sub-tasks with
  the full parent dataset. Where LegalBench-RAG only exposed yes/no
  classification accuracy, ContractNLI's gold evidence-span annotations let
  retrieval quality be scored directly rather than inferred from downstream
  answer correctness — a sharper DRM probe for RQ1, and the dataset most
  likely to expose whether SAC and hybrid retrieval find the right clause
  in a corpus of near-identical NDAs.

── TimeQA ───────────────────────────────────────────────────────────────────
Source:     wenhuchen/Time-Sensitive-QA (GitHub), Chen et al. 2021,
            NeurIPS Datasets & Benchmarks Track. Direct download, no
            registration.
Size:       The harness draws from the real test partition (dataset/test.easy.json
            + test.hard.json, ~3,000 template-generated question-answer pairs per
            split), sampling 1,000 questions per mode (2,000 total, fixed seed for
            reproducibility) covering time-evolving facts and relations mined from
            WikiData/Wikipedia.
Language:   English
Domain:     Temporal reading comprehension over Wikipedia pages describing
            facts that change over time (e.g. officeholders, team rosters).

Format:
  Each sample has:
    question   — a time-sensitive question, e.g. "Who was the president of
                 X between 1998 and 2002?"
    context    — the relevant Wikipedia passage
    answer     — gold answer span
    split      — "easy" (the time expression is explicit in the question)
                 or "hard" (the time expression must be inferred)

How it is evaluated:
  The model receives the passage and question and must extract or generate
  the answer span. Scoring follows the original paper's own protocol,
  reported separately for Easy and Hard:

  exact_match              — Binary: 1.0 if the prediction exactly matches
                              the gold span after normalisation.
  token_f1                 — Token-overlap F1 against the gold span
                              (SQuAD-style), reported per split.
  rouge_l                  — supplementary lexical overlap.
  temporal_consistency     — Fraction of any ISO-8601 dates in the answer
                              that exactly match the ground-truth date
                              string. Promoted from a legacy metric to a
                              primary one, since it is the sharpest direct
                              test of RQ3.
  perturbation_consistency — The paper's own robustness check: the time
                              expression in the question is perturbed (e.g.
                              shifted by a few years) and the metric checks
                              whether the model's answer changes accordingly
                              rather than staying fixed.

Significance:
  TimeQA replaces ChronoQA, which was Chinese-language. It keeps the
  Easy/Hard explicit-vs-implicit structure that made ChronoQA useful for
  RQ3, in English, and is a widely-cited, independently verifiable NeurIPS
  benchmark — unlike ChronoQA, whose primary source the dissertation could
  not independently verify at the time of the interim report. The system's
  deterministic date-arithmetic circuit should show its clearest advantage
  on the Hard split, where surface-level keyword matching cannot substitute
  for actual date reasoning.

── LoCoMo ────────────────────────────────────────────────────────────────────
Source:     Snap Research, via xjtuleeyf/Locomo-Plus (GitHub), locomo10.json
Size:       Ten long (~600-turn) multi-session conversations, 1,986 question-answer
            pairs total; the harness samples 1,000 of these (fixed seed, for
            reproducibility).
Language:   English
Domain:     Long-context conversational QA — factual memory score for RQ2.

Categories:
  1 — single_hop:   Direct factual recall from the conversation.
  2 — temporal:     Requires reasoning about when events occurred.
  3 — open_domain:  Requires world knowledge beyond the conversation.
  4 — multi_hop:    Requires chaining two or more facts from the conversation.
  5 — adversarial:  The question has a plausible-sounding wrong answer;
                    the model must resist it.

Format:
  Each session has:
    conversation  — dict of session keys, each a list of speaker/text turns
    qa            — list of {question, answer, category, adversarial_answer}
  The loader builds a 2000-char conversation context from all turns, then
  pairs each QA with that context.

How it is evaluated:
  The conversation context is prepended to the question. The model generates
  an answer. The primary metric uses an LLM-as-judge with category-specific
  prompts — one of five templates in _LOCOMOPLUS_PROMPTS, each adapted to
  the cognitive demands of that category. The judge returns a JSON verdict:
    {"verdict": "correct" | "partial" | "wrong", "reason": "..."}
  which maps to scores: correct=1.0, partial=0.5, wrong=0.0 (single_hop,
  multi_hop, open_domain are 3-level; temporal, adversarial are binary,
  correct=1.0/wrong=0.0). If the JSON parse fails, keyword detection on
  "correct"/"partial"/"wrong" in the raw output provides a fallback.

  judge_score  — LLM-as-judge verdict score, the primary metric.
  rouge_l      — supplementary; ROUGE-L against reference answer.

Significance:
  LoCoMo tests whether the system's session memory architecture actually
  helps with long-context factual recall — the hardest task for a RAG
  system, because the relevant context is spread across a long conversation
  history rather than indexed documents. The adversarial category directly
  tests resistance to confabulation.

── LoCoMo-Plus ───────────────────────────────────────────────────────────────
Source:     Li et al. 2026 extension, same GitHub repo (xjtuleeyf/Locomo-Plus),
            locomo_plus.json
Size:       401 cue-trigger instances — the whole benchmark, no sampling.
Language:   English
Domain:     Cue-trigger conversational recall — cognitive memory score for RQ2.

Format:
  Each item has:
    cue_dialogue    — the earlier conversational fragment
    trigger_query   — the later query that should activate the cue
    time_gap        — temporal distance between cue and trigger
  These are framed as "what connection does the earlier exchange have on this
  current situation?" questions, evaluated with the judge's "cognitive"
  category template — a past conversational cue should activate relevant
  future context without the model being explicitly reminded of it.

How it is evaluated:
  Same conversation-context-then-question protocol and LLM-as-judge
  mechanism as LoCoMo (see above), using the sixth, "cognitive" category
  template in _LOCOMOPLUS_PROMPTS (binary: correct=1.0/wrong=0.0):
    "Evaluate if the prediction demonstrates awareness of the connection
    between earlier context and the query."

  judge_score             — LLM-as-judge verdict score (cognitive template).
  constraint_consistency  — LLM-as-judge prompt: "Does the answer respect
                 the earlier cue (passed as the sole 'constraint')?" Binary
                 0/1 verdict — the direct test of whether the cue is being
                 applied, not just recalled.
  rouge_l      — supplementary; ROUGE-L against the cue text.
  exact_match  — supplementary; exact match after normalisation.

  Note: string-overlap metrics (rouge_l, exact_match) are biased by answer
  length and phrasing on this kind of open-ended connection-finding task;
  they are retained here for cross-checking only — judge_score and
  constraint_consistency are the headline metrics for this benchmark.

Significance:
  LoCoMo-Plus isolates the specific capability LoCoMo's categories don't
  test directly: spontaneously applying an earlier, low-salience cue to an
  unrelated-looking later request, without being asked to make the
  connection. constraint_consistency directly targets the retain-vs-apply
  distinction RQ2 is built around.

── CaseHOLD ──────────────────────────────────────────────────────────────────
Source:     reglab/casehold (accessed via coastalcph/lex_glue, config=case_hold)
Size:       1,000 test samples (full dataset: ~53,000)
Language:   English
Domain:     US case law — judicial holding selection from citing decisions

Format:
  Each sample has:
    context   — a citing passage from a court opinion, containing a "[HOLDING]"
                blank where a legal holding should be placed
    endings   — list of 5 candidate holdings (A through E)
    label     — integer 0-4 indicating the correct holding

  Note: the original reglab/casehold repository uses a deprecated HuggingFace
  dataset loading script (casehold.py) that is no longer supported. We access
  the identical data via the Parquet-format redistribution in coastalcph/lex_glue
  under the "case_hold" configuration, which loads without any custom script.

How it is evaluated:
  The model is presented with the citing text and the five options formatted as:
    "A. {holding_0}\nB. {holding_1}\n...\nAnswer with only the letter A-E:"
  The response is parsed for the first letter (A-E) or digit (0-4) in the
  first 20 characters. The predicted index is compared to the gold label.

  macro_f1  — Macro-averaged F1 across the 5 holding classes, matched to
              gold labels. This is the original paper's actual headline
              metric (Zheng et al., 2021, ICAIL), not raw accuracy, since
              class balance can otherwise mask systematic errors on
              particular holding types.
  accuracy  — 1.0 if predicted index equals gold label, else 0.0. Kept as
              a simple secondary check alongside macro_f1.
  rouge_l   — supplementary; ROUGE-L of generated response against the
              correct holding text.

Significance:
  CaseHOLD is a multiple-choice benchmark, the only one in the suite.
  It tests whether the model can perform holding-level legal reasoning —
  distinguishing subtle differences between five plausible-sounding holdings.
  Random baseline = 0.20; a good model should be significantly above this.
  Unlike the other five datasets, none of the system's four architectural
  components (SAC, hybrid retrieval, session memory, temporal circuit) have
  much to act on here — the full citing passage and all five candidates are
  handed to the model directly, with nothing to retrieve and no dialogue
  history. Scores across configurations are expected to cluster closely,
  with any edge from mixtral_cluster coming from model scale rather than
  pipeline design.

── CUAD (Contract Understanding Atticus Dataset) ────────────────────────────
Source:     chenghao/cuad_qa (HuggingFace, SQuAD-format)
            [Note: theatricusproject/cuad only has raw PDFs; chenghao/cuad_qa
            provides the pre-processed SQuAD-format version]
Size:       1,000 answerable questions drawn from the test partition
            (unanswerable questions are excluded by checking if answers.text
            is non-empty)
Language:   English
Domain:     Contract clause extraction — 41 clause types across 510 contracts

Format:
  Each sample has:
    question    — a clause-type question, e.g. "What is the governing law?"
    context     — the relevant contract excerpt (up to 2000 chars)
    answers     — dict with:
                  text: list[str]  — one or more gold answer spans
                  answer_start: list[int]  — character offsets

How it is evaluated:
  The model receives the contract excerpt and question, and generates a span
  (or paraphrase) of the answer. Because there may be multiple valid gold
  spans, all metrics take the maximum across all gold answers:

    best_em    = max(exact_match(pred, a) for a in gold_answers)
    best_tf1   = max(token_f1(pred, a)   for a in gold_answers)
    best_rouge = max(rouge_l(pred, a)    for a in gold_answers)

  exact_match  — Binary: 1.0 only if the prediction exactly matches any gold
                 span after lowercasing and whitespace normalisation.
  token_f1     — Token overlap F1 against the best-matching gold span.
  rouge_l      — supplementary; ROUGE-L against the best-matching gold span.
  AUPR         — Area under the precision-recall curve, over confidence-
                 ranked predictions. This is the original paper's actual
                 headline metric (Hendrycks et al., 2021), not EM/F1.
  precision_at_recall (r=0.8, r=0.9) — Precision once recall reaches the
                 stated threshold, matching the paper's P@80%R and P@90%R
                 figures directly.

Significance:
  CUAD tests span extraction from long contracts — the closest task in the
  suite to what the system's core use case actually is (legal document QA).
  It has the most unforgiving exact_match scoring (any deviation = 0), and
  AUPR/precision_at_recall reproduce the paper's own primary evaluation
  protocol rather than only the SQuAD-style secondary metrics.

── RETIRED DATASETS ──────────────────────────────────────────────────────────
LexRAG and ChronoQA were both dropped for being Chinese-language, which
introduced a cross-lingual confound unrelated to the architecture under
test. LegalBench-RAG was superseded by ContractNLI (its own parent dataset,
with gold evidence spans). LexGLUE was dropped as a redundant generalisation
check once CaseHOLD already provides one, at the cost of extra metric
complexity (micro-F1 across two multi-label sub-tasks) for limited added
insight. The dataset-loading code for all four has been removed from the
codebase entirely — not merely excluded from the standard run — along with
their data/eval/*.json files and dedicated Slurm sbatch jobs.

7c. THIRTEEN METRICS
--------------------------------------------------------------------------------

All metric implementations are in backend/evaluation/metrics.py.
None require NLTK or any external model beyond what is already running;
the LLM-as-judge metrics use the local llama3.1:8b via Ollama.

  rouge_l
    ROUGE-L F1 via pure-Python LCS (Longest Common Subsequence). No NLTK.
    Measures lexical overlap; robust to paraphrase ordering. Supplementary
    everywhere it appears — cross-checked against a stricter primary metric,
    never reported alone.
    Used by: all 6 benchmarks.

  accuracy
    Binary 0/1. Exact match of predicted class label to gold.
    Used by: ContractNLI (3-way NLI label), CaseHOLD (secondary alongside
    macro_f1).

  macro_f1
    F1 averaged across the 5 holding classes rather than pooled over all
    predictions, so a class the model gets systematically wrong isn't
    masked by good performance on the others.
    Used by: CaseHOLD (primary metric, per Zheng et al., 2021).

  micro_f1
    Per-sample F1 between predicted set and gold set, averaged across
    samples: tp = |pred ∩ gold|, precision = tp/|pred|, recall = tp/|gold|,
    F1 = 2pr/(p+r).
    Used by: ContractNLI (evidence span identification, treated as
    multi-label classification over candidate spans).

  exact_match
    Binary 0/1. Exact string match after lowercasing and stripping whitespace.
    Used by: CUAD, TimeQA (Easy/Hard), LoCoMo-Plus (supplementary).

  token_f1
    Token-overlap F1. Tokenise by whitespace, compute precision/recall on
    unique token sets. Same formulation as SQuAD official metric.
    Used by: CUAD, TimeQA (Easy/Hard).

  AUPR
    Area under the precision-recall curve over confidence-ranked
    predictions.
    Used by: CUAD (primary metric, per Hendrycks et al., 2021).

  precision_at_recall(r)
    Precision once recall reaches the threshold r, parametrised so the
    same implementation covers every paper's own reporting convention.
    Used by: CUAD (r=0.8 and r=0.9, matching P@80%R / P@90%R), ContractNLI
    (r=0.8, matching the paper's own P@R0.8 evidence-identification metric).

  judge_score
    LLM-as-judge with 6 category-specific prompt templates, 5 for LoCoMo
    (single_hop, multi_hop, temporal, open_domain, adversarial) and 1
    ("cognitive") for LoCoMo-Plus. Per the source paper's protocol: 3-level
    verdict ("correct"|"partial"|"wrong" → 1.0/0.5/0.0) for the factual and
    open-domain categories, binary verdict ("correct"|"wrong" → 1.0/0.0)
    for temporal, adversarial, and cognitive categories.
    Fallback: keyword scan of raw response if JSON parse fails.
    Used by: LoCoMo (primary), LoCoMo-Plus.

  constraint_consistency
    LLM-as-judge prompt: "Does the answer respect the stated constraint(s)?"
    Binary 0/1 verdict. For LoCoMo-Plus, the "constraint" passed is the
    earlier cue_dialogue — the direct test of RQ2's cognitive-memory half:
    whether an implicit cue is still being applied, not just recalled.
    Implemented and computed by the harness, but NOT one of the headline
    metrics reported in the dissertation's results chapter (LoCoMo-Plus's
    reported metrics are judge_score, exact_match and rouge_l only).
    Used by: LoCoMo-Plus.

  temporal_consistency
    Fraction of predicted ISO-8601 date strings matching ground_truth_dates
    exactly. Zero-tolerance string match. Distinct from perturbation_consistency
    below. Implemented by the harness but, unlike perturbation_consistency,
    NOT one of the metrics reported in the dissertation's results chapter —
    it remains a harness-only diagnostic, not a headline result.
    Used by: TimeQA.

  perturbation_consistency
    The time expression in the question is perturbed (e.g. shifted by a
    few years) and the metric checks whether the model's answer changes
    accordingly rather than staying fixed — the source paper's own
    robustness check. This IS one of the reported headline metrics
    (TimeQA's "Consistency" column in the results).
    Used by: TimeQA.

  retrieval_recall
    For each gold span (ContractNLI's evidence spans), the first 5
    non-trivial tokens (len > 2) are extracted. A span is "recalled" if any
    of these probe tokens appear in the concatenated retrieved texts.
    Repurposed from the earlier golden_chunks-based heuristic (previously
    used by the now-dropped LexRAG/ChronoQA) onto ContractNLI's own
    gold-span annotations. CUAD is closed-book (the excerpt is given
    directly with the question, not retrieved), so it does not use this
    metric. Implemented and computed by the harness, but NOT one of the
    headline metrics reported in the dissertation's results chapter
    (ContractNLI's reported metrics are NLI accuracy, evidence P@R0.8 and
    evidence set F1 only).
    Used by: ContractNLI.

  Note: constraint_consistency, temporal_consistency and retrieval_recall
  are three of the thirteen implemented metrics that the dissertation
  explicitly describes as implemented by the harness but excluded from
  its reported results (Section 3.9.3): "The harness also implements
  three metrics that are not part of the reported results, i.e., a
  temporal consistency score over ISO-8601 dates, a separate
  constraint-consistency judge, and a retrieval recall based on probe
  tokens from the gold spans." Only 20 metric x dataset combinations
  from the remaining ten metrics appear in the dissertation's Table 4.1.

RETIRED METRICS (implementation retained in metrics.py, not part of
standard reporting): keyword_accuracy, contextual_accuracy, faithfulness.
All three were anchored only to LexRAG's legacy general pipeline; with
LexRAG's loading code removed from the codebase entirely, none of the six
current benchmarks exercise them.

  The notes field carries per-sample metadata as a JSON object:

PART B: FOR A SOFTWARE ENGINEER WHO DOES NOT KNOW ML

WHAT IS THIS SYSTEM?
--------------------
Think of it as a very specialised search engine plus Q&A assistant built
specifically for legal documents. You upload a PDF (e.g. an International
Criminal Court ruling). You ask a question. It finds the relevant sections
of the PDF and writes you an answer citing exactly which page it used.

There are no "hallucinations" (making things up) because the system is
designed to refuse to answer anything not explicitly found in the documents:
if it can't find it, it says "I could not find this information in the
provided documents." This refusal is enforced by the instructions we put in
the system prompt — it's not magic, it's just a very firm instruction.

The whole thing is a standard web application: React frontend, FastAPI
backend, PostgreSQL database, and a vector database called Qdrant.
The "AI" parts are just external services you call like any other API.

--------------------------------------------------------------------------------
1. HOW DOCUMENTS GET STORED (INGESTION)
--------------------------------------------------------------------------------

When you upload a PDF, the system does three things:

STEP 1: READ THE PDF
We use a library called PyMuPDF to extract text from each page, keeping
track of which page number each piece of text came from. We tried another
library (pypdf) but it mangled the text in some legal PDFs — the characters
came out spaced like "T h e   l a w". PyMuPDF handles the font encoding
correctly, so we switched.

STEP 2: CUT IT INTO PIECES (CHUNKS)
A 400-page PDF is too big to search all at once. So we cut it into 512-
character overlapping pieces called "chunks". Think of it like cutting a
long newspaper article into paragraphs with slight overlap between consecutive
paragraphs, so sentences at the boundary aren't lost.

For legal documents, we also prepend a short 150-character summary of the
whole document to every chunk. Why? Because a user might ask "what is the
legal basis?" — that's vague language. But a chunk from page 12 might only
say "...pursuant to Article 25(2)(b) of the Rome Statute...". Without the
summary prefix, the search system doesn't know those two things are related.
The summary acts as a shared vocabulary bridge between vague questions and
specific text fragments.

We also throw away chunks shorter than 80 characters. Legal PDFs often have
repeated page headers like "ICC-01/14-01/18   Page 11/22" — those are
useless and pollute search results.

STEP 3: CREATE TWO TYPES OF INDEX ENTRIES
For each chunk, we create two numbers-based representations and store both
in Qdrant (the vector database):

  a) DENSE VECTOR (semantic): A 768-number array that represents the
     "meaning" of the chunk. Generated by a local embedding model
     (nomic-embed-text). Conceptually: chunks that mean similar things
     get similar number arrays, regardless of exact words used.
     This is like finding synonyms automatically.

  b) SPARSE VECTOR (keyword): A simplified keyword-frequency index.
     We count how often each unique word appears and represent that as
     a sparse array (most entries are zero). This is essentially old-school
     keyword search (like grep, but weighted by frequency).

Both get stored together in Qdrant. We also write metadata (filename,
page number, chunk text) to PostgreSQL as a normal database record.

--------------------------------------------------------------------------------
2. HOW QUESTIONS GET ANSWERED (RETRIEVAL + GENERATION)
--------------------------------------------------------------------------------

When you type a question, it goes through a pipeline:

STEP 1: FIND RELEVANT CHUNKS (HYBRID SEARCH)
Your question is also converted to both a dense vector and a sparse
keyword vector (same process as documents). Qdrant is asked:
"Find me the 16 chunks most similar to this question by semantic meaning,
AND the 16 chunks most similar by keyword overlap."

Then it combines those two ranked lists using an algorithm called
Reciprocal Rank Fusion (RRF). RRF works like this:
  - Something ranked #1 in list A gets score 1/(60+1) = 0.016
  - Something ranked #1 in list B also gets 0.016
  - If the same chunk appears in both lists, those scores add up
  - The chunk with the highest combined score wins

Result: chunks that are both semantically relevant AND keyword-relevant
rank highest. This is more robust than either approach alone. (A chunk
that uses exact words but wrong meaning would rank well on keywords but
poorly on semantics — the hybrid punishes it.)

The top 8 results are passed to the next step. There's also a reordering
trick: the most relevant chunk is placed first, the second-most-relevant
is placed last, and the rest fill the middle. This is because language
models pay more attention to the beginning and end of input text, so
we put the best evidence in high-attention positions.

STEP 2: DECIDE HOW TO HANDLE THE QUESTION (ROUTING)
The system classifies every question into one of three categories before
generating an answer:

  TEMPORAL: Does the question mention words like "deadline", "within",
  "statute of limitations", "expiry", "notice period"?
  → Trigger the date-calculation system (see Section 4).

  SIMPLE: Short question, no complex analysis requested?
  → Answer locally using llama3.1:8b (a medium-sized language model
    running on your own machine).

  COMPLEX: Long question (>40 words) or contains words like "analyse",
  "compare", "critically examine", "what are all the implications of"?
  → Send to the Warwick University GPU cluster running Mixtral 8x7B,
    a much larger and more capable model. Or, if the user explicitly
    clicked "Use Mixtral" in the UI, always go to cluster.

This routing decision is made with a few if-statements scanning the
query text — no AI involved in the routing itself.

STEP 3: BUILD THE PROMPT AND GENERATE AN ANSWER
The system assembles a big text prompt that looks like this (roughly):

  [PERMANENT RULES]: Always answer in English. Never discuss X.
  [SESSION RULES]: Only consider UK law for this conversation.
  [YOUR ROLE]: You are a contract law expert.
    You may ONLY use information from the retrieved context below.
    If you can't find the answer, say "I could not find..."
    Always cite the source document and page number.
  [DOCUMENT EXTRACTS]:
    [LEGAL DOCUMENT — katanga_ruling.pdf, page 4]:
    ...the Pre-Trial Chamber found that the accused bears responsibility...
    [LEGAL DOCUMENT — katanga_ruling.pdf, page 7]:
    ...pursuant to Article 25(2)(b) of the Rome Statute...
  [CONVERSATION SO FAR]: User asked about liability, we said...
  [RECENT MESSAGES]: last 4 messages verbatim

This prompt is sent to the language model. The model reads all the document
extracts and writes an answer. Because we told it it can ONLY use those
extracts, it can't invent facts.

The answer streams back word-by-word (like ChatGPT's typing effect) over a
persistent HTTP connection (Server-Sent Events / SSE). The frontend also
shows which document page was cited.

For Mixtral on the cluster: the same prompt is written to a JSON file on a
shared network drive, a job is submitted to the university's job scheduler
(Slurm — like a queue for GPU jobs), the cluster reads the file and runs
Mixtral, writes the answer to another file, and our system polls for that
file. The SSE stream stays open the whole time so the user sees a "waiting
for cluster..." message. Mixtral is too large to run locally (90GB+ of
weights) but fits on a university GPU with 4-bit compression.

--------------------------------------------------------------------------------
3. HOW THE SYSTEM REMEMBERS PREVIOUS QUESTIONS (SESSION MEMORY)
--------------------------------------------------------------------------------

Everything is stored in PostgreSQL like a normal web app. The tables are:
  sessions    — one row per conversation (has title, is_active flag)
  messages    — one row per message (user or assistant), foreign key to session
  constraints — rules the user has set ("only use UK law"), FK to session

CONSTRAINT EXTRACTION
Every time you send a message, a small language model (llama3.2:3b) scans
it for rules you might be setting. If you say "only consider EU law for this
conversation", it extracts jurisdiction=EU and saves it to the constraints
table. If you say "always, in every session, ignore confidentiality clauses",
it marks is_permanent=True and that constraint applies to every future
conversation you have.

This is essentially a lightweight NLP-based form parsing system — parsing
rules out of natural language instead of dropdowns.

COMPRESSION
After every 10 messages, the system takes all but the last 4 messages and
asks llama3.1:8b to summarise them into a factual paragraph. This summary
is saved to the sessions table. From then on, instead of sending 30 messages
of history in every prompt (which would overflow the context window), it
sends just the summary paragraph + last 4 raw messages. This keeps the
prompt size bounded regardless of conversation length.

Think of it like a rolling log file with automatic rotation — instead of
appending forever, old entries get compressed into a summary.

--------------------------------------------------------------------------------
4. THE DATE CALCULATION SYSTEM (TEMPORAL REASONING)
--------------------------------------------------------------------------------

Legal questions often involve dates and deadlines: "When does the appeal
window close?" "Is the statute of limitations expired?" These are not
questions a language model answers reliably — they require actual date
arithmetic, not pattern-matched text generation.

The temporal system intercepts any question containing date-related keywords
and runs a two-stage process:

STAGE 1: EXTRACT DATES (LLM call)
llama3.2:3b is asked to read the question + retrieved document chunks and
output structured JSON listing:
  - All explicit dates (with what they refer to)
  - Trigger events (events that start a time window)
  - Relative references ("within 30 days", "no later than 60 days after")

STAGE 2: CALCULATE DEADLINES (pure code, no LLM)
Two Python functions run on the extracted JSON:

  parallel_circuit: Finds the earliest and latest date in the list.
    Checks if any "within N days" reference is violated by the date range.
    (A document saying "within 30 days" but having dates 45 days apart is
    flagged as a contradiction.)

  series_circuit: Finds the earliest trigger event, adds the rule_days
    from the relative references, and calculates a deadline date.
    e.g. trigger date 2024-01-15 + "within 30 days" = deadline 2024-02-14.

The computed dates (earliest, latest, deadline, any conflicts) are shown
to the user in a dedicated date card in the UI, separate from the text
answer. This makes the date calculations auditable — you can verify the
arithmetic without trusting the model.

The design principle is: use AI for the messy part (understanding natural
language dates in legal text), then use deterministic code for the reliable
part (actual date arithmetic). Never let a language model do calendar math.

--------------------------------------------------------------------------------
5. HOW THE EVALUATION WORKS
--------------------------------------------------------------------------------

The goal is to scientifically compare how much better the full system is vs
simpler baselines. This is what makes it a dissertation rather than just
a product.

WHAT WE COMPARE — FIVE SYSTEM CONFIGURATIONS
Each configuration is a version of the system with some features turned on
or off. Running all five against the same questions shows what each feature
contributes.

  vanilla_rag
    The dumbest possible version. Basic keyword+semantic search fetching only
    5 chunks, simple flat prompt, no routing, no memory, no structure.
    This is the "floor" — everything should beat this.

  long_ctx_only
    Same dumb search but fetches 15 chunks instead of 5 and dumps them all
    into the prompt. Tests whether just "more context = better answers" is true
    (spoiler: not necessarily — more context also means more noise).

  self_route_base
    Adds proper hybrid search (keyword + semantic combined) and routing
    (temporal questions go to the date calculator, complex ones go to the
    cluster). Basic expert-role prompt, but no memory or full prompt structure.
    This isolates the contribution of smart retrieval and routing.

  full_system
    Everything switched on: hybrid search, routing, structured 7-section prompt
    with grounding rules, session memory, constraint tracking, compression.
    This is the dissertation's main system.

  mixtral_cluster
    Identical to full_system but the answer is generated by Mixtral 8×7B
    (a much larger model on the university GPU cluster) instead of the local
    llama3.1:8b. Tests whether paying for a bigger model meaningfully improves
    quality on top of the pipeline improvements.

WHAT WE MEASURE — SIX BENCHMARK DATASETS
We test against six different publicly available legal/NLP AI datasets,
all in English (an earlier version of the suite included two
Chinese-language datasets — LexRAG and ChronoQA — which were dropped
entirely, since testing a mostly-English system on Chinese text measures
translation ability as much as it measures the architecture). Each
remaining dataset maps onto one of the three research questions (RQ2 gets
two datasets — a factual-memory one and a cognitive-memory one, since
those are genuinely different skills), plus one held-out generalisation
check. Here is what each one is and why it matters:

  CUAD (English contract clause extraction — 1,000 samples)
    Given a real contract excerpt and a question like "What is the
    governing law clause?" or "Is there a non-compete provision?", extract
    the exact text from the contract. The gold answer is a specific span
    of text.
    WHY: Closest to the system's actual use case (contract analysis). The
    scoring is strict — your extracted text must exactly match the gold
    span to get full marks. Feeds RQ1.

  ContractNLI (English NDA reasoning — 607 contracts, 1,000 of 2,091 test pairs)
    Given a non-disclosure agreement and a statement like "Some obligations
    survive termination," decide whether the contract confirms it, denies
    it, or doesn't mention it at all — and point to exactly which sentences
    in the contract support that answer.
    WHY: Replaces an earlier dataset (LegalBench-RAG) that only checked
    whether the final Yes/No answer was right. ContractNLI also checks
    whether the system found the *right sentences* to justify that answer,
    which is a much closer test of whether retrieval is actually finding
    the correct passage rather than just guessing the right label. Feeds
    RQ1.

  LoCoMo (English conversational memory — 1,000 of 1,986 questions)
    A long conversation between two people is given as context, then the
    system is asked questions that require remembering details from earlier
    in the conversation. Five categories: simple recall, temporal,
    open-domain (world knowledge beyond the conversation), multi-hop (chain
    two facts), and adversarial (resist a plausible-sounding wrong answer).
    WHY: Tests whether the system's session memory architecture helps with
    long-context factual recall. The adversarial category tests
    hallucination resistance. Feeds the factual half of RQ2.

  LoCoMo-Plus (English cognitive memory — 401 cue-trigger instances)
    An extension of LoCoMo: a cue is mentioned early in a conversation
    (e.g. the user mentions an upcoming exam), and much later a seemingly
    unrelated request arrives (e.g. asking for TV recommendations). The
    system must factor in the earlier cue without being explicitly
    reminded of it.
    WHY: Tests the harder, more implicit half of session memory — applying
    a constraint the user never restated, not just answering a direct
    question about something they said. Feeds the cognitive half of RQ2.

  TimeQA (English temporal reasoning — 2,000 samples, 1,000 per mode)
    Questions about facts that changed over time — e.g. "who held office
    between these two years" — split into "easy" questions (the date is
    spelled out in the question) and "hard" questions (the system has to
    work out the relevant time period itself).
    WHY: Replaces ChronoQA, which was Chinese-language. TimeQA tests the
    same explicit-vs-implicit date reasoning, in English, using a dataset
    from a peer-reviewed NeurIPS paper with a properly documented source
    (unlike ChronoQA, whose original paper the dissertation could not
    fully verify). Feeds RQ3.

  CaseHOLD (English US case law — 1,000 samples)
    Multiple-choice legal exam. Given a real court decision with a blank
    where a holding (legal conclusion) should be, pick the correct one from
    five options (A through E). Guessing randomly gets 20%; a good system
    should be well above that.
    WHY: Tests fine-grained legal reasoning — distinguishing between very
    similar-sounding legal conclusions — as a held-out generalisation check.
    Nothing here needs to be retrieved and there's no conversation history,
    so it's a useful sanity check for whether the model can reason at all,
    separately from whether the pipeline's extra machinery helps.

HOW SCORES ARE COMPUTED — THIRTEEN METRICS
Different tasks need different measurement approaches. Each dataset below
uses whichever of these its own original research paper uses, so our
numbers can be compared against published results rather than against a
metric we invented ourselves.

  ROUGE-L (used everywhere, as a supplementary check)
    Measures how much the answer overlaps word-for-word with the reference
    answer. "The court held that Article 25 applies" vs "Article 25 was held
    to apply by the court" — different order, but lots of shared words = decent
    ROUGE score. Score is 0 to 1; higher is better. Never the headline metric
    on its own — always paired with something stricter.

  Accuracy (ContractNLI, CaseHOLD)
    Simple right/wrong percentage. Did the model pick the correct label
    (Entailment/Contradiction/NotMentioned, or the correct multiple-choice
    option)? 1.0 = always right, 0.0 = always wrong.

  Macro-F1 (CaseHOLD)
    Like accuracy, but averaged evenly across the five possible holding
    types rather than lumped together. This stops a model that's great at
    one type of holding and terrible at another from looking "fine on
    average" — it's the actual headline metric the CaseHOLD paper uses.

  Micro-F1 (ContractNLI)
    When there are multiple correct pieces of evidence (e.g. "sentences 3,
    7, and 12 of this contract support the answer"), we measure how many of
    the correct ones the system found (recall) and how many of its guesses
    were actually correct (precision). F1 combines both into one score.

  Exact Match (CUAD, TimeQA)
    Strictly binary: 1.0 only if the answer is character-for-character identical
    to the reference (after lowercasing). Harsh but unambiguous.

  Token F1 (CUAD, TimeQA)
    Same idea as Micro-F1 but for individual words in the answer vs words in
    the reference. More forgiving than Exact Match — partial credit for
    getting most words right.

  AUPR (CUAD)
    Area Under the Precision-Recall curve. Instead of one right/wrong score,
    this looks at how good the system's answers are across its full range
    of confidence levels. This is the actual headline number CUAD's own
    paper reports, not just Exact Match.

  Precision-at-Recall (CUAD, ContractNLI)
    "Once we've correctly found 80% (or 90%) of what we were supposed to
    find, how much of what we're returning is actually correct?" This
    matches how both CUAD's and ContractNLI's original papers report their
    results, so our numbers line up with published figures.

  Retrieval Recall (ContractNLI)
    Did we actually retrieve the right passages from the document? The
    dataset tells us exactly which text (the gold evidence sentences)
    should have been retrieved. We check if that text appears in what we
    retrieved. 1.0 = got everything needed. (CUAD is closed-book — the
    contract excerpt is given directly with the question rather than
    retrieved — so this metric doesn't apply there.) The harness computes
    this, but it is not one of the numbers in the dissertation's results
    chapter — ContractNLI's reported figures are NLI accuracy, evidence
    P@R0.8 and evidence set F1.

  LLM Judge Score (LoCoMo, LoCoMo-Plus)
    A separate AI model reads the question, the reference answer, and our
    answer, then judges it. For simple factual/open-domain questions:
    "correct", "partially correct", or "wrong" (1.0/0.5/0.0). For temporal,
    adversarial, and cognitive (LoCoMo-Plus) questions: just "correct" or
    "wrong" (1.0/0.0) — this is the same scheme the LoCoMo-Plus paper
    itself uses, since those question types don't really have a
    "half-right" answer.

  Constraint Consistency (LoCoMo-Plus)
    "Earlier in the conversation, the user mentioned X — does this answer
    still factor that in?" An AI judge checks whether the earlier cue is
    still being applied, not just whether the model can recall that it was
    mentioned. This is the sharpest test of whether the session-memory
    feature applies information unprompted, rather than only when asked.
    The harness computes this, but it is not one of the numbers in the
    dissertation's results chapter — LoCoMo-Plus's reported figures are
    the LLM judge score, exact match and ROUGE-L.

  Temporal Consistency (TimeQA)
    If the answer contains a date, does it match the correct date exactly?
    No partial credit — this directly tests the deterministic date-
    arithmetic circuit rather than the model's general fluency. This is a
    different metric from Perturbation Consistency below, and unlike it,
    the harness computes but does not report Temporal Consistency in the
    dissertation's results chapter.

  Perturbation Consistency (TimeQA)
    We nudge the date mentioned in the question by a few years and check
    whether the answer changes accordingly. A system that gives the same
    answer regardless of what date you ask about clearly isn't actually
    reasoning about time — this metric catches that. This one IS reported
    in the dissertation's results chapter, as TimeQA's "Consistency" score.

6. HOW TO USE THE EVALUATION DASHBOARD
--------------------------------------------------------------------------------

There is no "Download All Datasets" button in the UI — this was a
deliberate choice, not a missing feature. Getting the data into
data/eval/ is a one-time setup step done outside the app, before you ever
open the Evaluation tab:

STEP 1 — GET THE DATASETS (one-time setup, outside the app)
  LoCoMo/LoCoMo-Plus, CaseHOLD, CUAD — run
    `python backend/evaluation/download_datasets.py` from a terminal. This
    fetches these three from GitHub/HuggingFace and saves them to data/eval/.
  ContractNLI, TimeQA — there's no script for these two. Fetch them
    yourself from their original sources (Stanford NLP Group's
    contract-nli.zip; wenhuchen/Time-Sensitive-QA's GitHub test partition)
    and place the transformed files at data/eval/contractnli.json and
    data/eval/timeqa.json — see benchmarks.py's loader docstrings for the
    exact expected field names.
Either way, this only needs to be done once — the files are cached locally
and the Evaluation tab reads directly from data/eval/.

STEP 2 — RUN A BENCHMARK
Select from three dropdowns:
  Dataset — which benchmark to run (or "all" for all six)
  Config  — which version of the system to test (or "all" for all five)
  Max samples (n) — optional number limit. Leave blank to run the full
    dataset. Set e.g. "10" to do a quick sanity check first.

Click "Run Evaluation". The benchmark runs in the background — you can
close the tab and come back later. Results update automatically.

STATUS BAR
Below the run controls is a persistent status bar that always shows what
is happening:
  Gray / "No evaluations running" — nothing is in progress.
  Amber / spinning indicator — shows which benchmark:config combinations
    are currently running. Each running job shows a Stop button.

STOPPING A BENCHMARK
Each running job chip in the status bar has a "Stop" button. Clicking it
sends a stop signal to the server. The benchmark will finish processing the
current sample and then stop — partial results are saved and visible.

THE STATUS BAR ALWAYS SHOWS THE TRUE SERVER STATE
The frontend polls the server every 5 seconds regardless of what you clicked
locally. Even if you refreshed the page, it will correctly show any benchmarks
that are still running from before. When a benchmark finishes, the results
table and chart update automatically within 5 seconds.

VIEWING RESULTS
The bar chart shows each metric on the X-axis and scores (0-1) on the Y-axis.
Each coloured bar is one configuration. Hover over bars for exact scores.
Use the "Filter dataset" and "Filter metric" dropdowns to narrow down what
you're looking at. The results table below shows every individual row with
the per-sample metadata (which task, temporal type, category, etc.) shown
as small tags.

DELETING RESULTS
Click "Clear Results" to delete result rows. By default it deletes results
for the currently filtered dataset only. To delete everything, set the filter
to "all" first. A two-click confirmation ("Yes, delete" / "Cancel") prevents
accidental deletion.

9. WHAT MAKES THIS A RESEARCH PROJECT
--------------------------------------------------------------------------------

The three things that differentiate this from a generic "chat with your PDF"
tool and make it dissertation-worthy:

1. HYBRID RETRIEVAL WITH RRF: Most tutorials use dense-only search. Dense
   search is better at semantic similarity, keyword search is better at
   rare technical terms (case citations, statute numbers). Combining both
   demonstrably improves retrieval quality — this is measurable via the
   retrieval_recall metric on ContractNLI, and via ContractNLI's
   evidence-identification precision_at_recall and micro_f1.

2. SUMMARY-AUGMENTED CHUNKING: The "lost in the middle" problem is a known
   weakness of RAG. Attaching a document-level summary to every chunk is
   a published technique we implement and evaluate. The question is: does
   it actually help on legal text, which has a specific vocabulary?
   The full_system vs self_route_base comparison isolates this.

3. TEMPORAL REASONING CIRCUIT: Language models are unreliable at date
   arithmetic. Extracting structured dates and running deterministic
   calculations is a hybrid AI/classical approach. TimeQA (1,000 samples
   per Easy/Hard split, drawn from the real test partition) directly tests
   this with exact_match, token_f1, and the promoted temporal_consistency
   and perturbation_consistency metrics on temporal answers.

4. SCALE OF EVALUATION: Six benchmarks × five configs × thirteen metrics
   = a multi-dimensional comparison matrix that goes well beyond the typical
   dissertation which runs on one or two custom datasets. All six are
   established, English-language datasets from the legal/NLP literature —
   one per research question (two for RQ2's factual/cognitive split) plus
   one generalisation check — making the results comparable to published
   work without a cross-lingual confound.

The quantitative evidence from this matrix — which configs outperform which
baselines, by how much, on which types of tasks — is what the dissertation
argument is built around.
